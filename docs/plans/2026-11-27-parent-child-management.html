Managing child Nathan instances

Give the gmacko parent at id.gmac.io one Studio view of its children. Each child owner chooses what the parent can read, which changes it can make, and whether people can sign in through the parent.

First release milestoneEnroll one owned-domain staging child. Read its health, perform one explicitly granted role change, revoke the link from the child, and confirm the same credential immediately loses access. The child’s local administrator must still be able to sign in.

The child’s private signing keys, passwords, sessions, provider secrets, MFA policy, and Cloudflare account credentials stay under child control. The parent’s Workers hold only their own per-child credentials. Human admin access keeps its existing Access and Nathan checks. The machine API has a fixed route, audience, and explicit action list.

Delivery sequence

1 · Registry and enrollment NATH-27 · An owned child appears in the parent after local consent.
  1. A verified parent operator selects an exact child issuer. Parent Studio creates a pending invitation bound to the two issuer identities, an enrolled parent public key and an expiry. Store a digest of the one-time code. Bound attempts and redact it from logs.
  2. The local child owner uses their authenticated Studio to open the invitation. Show both canonical issuers, ownership, the parent key fingerprint and requested capabilities. Start each permission unchecked. Require recent verification to confirm.
  3. Each side proves control of its advertised issuer and key through verified HTTPS and a fresh challenge. Pin the expected identity and registered endpoints. Validate all network destinations, disallow redirects and private, link-local or metadata addresses, and bound time and response size. Do not resolve arbitrary URLs from an operator’s browser request.
  4. Redeem once in a transaction. Persist a stable enrollment ID, then acknowledge using that same ID at both ends. Repeated acknowledgments converge. An interrupted exchange stays pending and authorizes no operations. A revoked relationship requires fresh consent to re-enroll.

Storage. Parent D1 holds children, invitations, per-child operator grants and operation receipts. Child D1 holds parent links, granted scopes, accepted public keys, grant revision and receipts. Use migrations with unique issuer pairs and enrollment IDs. Store parent private key material in protected Worker secret storage or encrypted under a per-deployment key.

2 · Read the fleet NATH-27 · Overview, child detail, stale health and last successful contact.

The parent authenticates to the child token endpoint using private_key_jwt with a short-lived assertion and one-use identifier. The child issues a machine access token for its exact management audience, with only approved scopes and a lifetime of at most 900 seconds. Verify support for this client authentication method with the installed Better Auth version before registering fleet clients.

Start with fleet:read for health, version, aggregate counts and a redacted audit summary. Paginate child lists and events. Use bounded concurrency and independent per-child timeouts. Record last contact and last success separately. A slow or offline child affects one row. Cached information carries a timestamp and is never used to authorize a write.

The child verifies the token, issuer, audience, expiry, client, link revision and active local scope on every request. Bind machine authorization to its own entry point and reuse the underlying services. Test that browser Studio, the directory API and sign-in tokens retain their existing boundaries.

3 · Scoped changes and audit NATH-27 · Child-side revocation also stops previously issued tokens.
CapabilityOperations the child can approve
fleet:admin.usersSelected admission or ordinary user lifecycle actions. Owner and administrator accounts require child-local administration.
fleet:admin.appsSelected app registration and enablement actions with exact redirects. Secret-returning operations stay local.
fleet:admin.rolesOrdinary app role grants and revocations identified by both app and grant. Reserve administrative roles and the fleet link for local management.

Start the pilot with one role mutation. Expand the action list only after testing the target and output of each service call. The parent checks the acting operator’s live authorization and recent step-up, then binds the operator identity, child, action, payload digest and operation ID to the request. Treat display names and caller-supplied identity headers as untrusted.

The child checks current grant revision during the mutation and records the result with its audit entry in one transaction. Identical retries reuse the stored result. Reject a reused operation ID with different content. If the response is lost, the parent reconciles by operation ID before offering retry. Both audits record parent issuer, operator subject, child, scope, target and outcome. Redact user data and all credentials.

4 · Optional parent sign-in NATH-28 · Child admission and local grants control the user’s access.

Build on the existing Nathan upstream provider work in NATH-51 and the enterprise OIDC policy. The child registers an explicit client on the parent with an exact callback, uses code flow with S256, and verifies issuer, signature, audience, state and nonce. Store the parent issuer and subject together. Apply child admission and explicit verified-link rules when a local account already exists.

Default auto-admission to off. A parent administrator starts with ordinary child access and needs a separate child-local grant and child assurance policy for administration. Preserve an independently authenticated local recovery owner. Disabling federation blocks new sign-ins and pending callbacks immediately. Track federated session provenance so the child can end those sessions under its stated disconnect policy without touching local owner sessions.

Show the active parent and all current grants in child Studio, with separate controls for federation, summaries and each mutation scope. A read-only management link and a federation-only link must each work on their own.

5 · Revoke, rotate, recover and release NATH-29 · Customer-owned installations follow the owned-domain pilot.

A child owner can suspend a scope, turn off federation, or disconnect locally while the parent is offline. A transaction advances the grant revision and disables affected credentials. Check the authoritative current revision on the child for each read and write. In-flight writes serialize with revocation. Purge cached child data according to the child’s retention policy and preserve redacted audit receipts.

For planned rotation, the child verifies the proposed new public key and proof of possession, allows a bounded overlap, then retires the old key. For emergency rotation, revoke first and re-enroll through the local owner. A service rollback keeps all revocation records and local recovery access intact. On a restored database, revalidate trust before re-enabling fleet operations.

Customer-account installation is owner-initiated. Keep a persistent linked-parent banner. Parent read, write and federation are separate opt-ins. Any future provisioning of an owned-domain child uses the existing installer as a separate operator action. Customer Cloudflare credentials remain in the customer account.

Rollout evidence and decisions

Sequence. Use two disposable Worker instances with separate D1 databases first. Deploy the reviewed revision to an explicitly designated owned-domain staging child, exercise enrollment through both Studios, then canary one owned production child. A customer pilot follows independent review and owner opt-in.

Evidence per stage. Record both issuers and versions, PR and merge revisions, deployment IDs, exact scope set, health and redacted operation IDs. Confirm an old token is refused after revocation, local recovery works and an unrelated child is unaffected. Keep fleet writes disabled if any release check fails.

Implementation decisions to settle. Choose the first owned staging child with its operator. Confirm per-child key custody and rotation facilities. Agree which aggregate fields, retention period and operator roles are appropriate for customer fleets. Until those are settled, exercise the minimal health summary and one ordinary app role in disposable instances.

Parallel program work. Verify Studio #34 and launch NATH-25. Finish the shared Better Auth provider and pilot Kanbanger before rolling “Sign in with gmacko” out across apps. App rollout and child management can progress independently after their own prerequisites.
