Nathan: Worker protection, RBAC and federation In progress

2026-11-21 · gmackie/nathan · base 73a8325 · issues NATH-8, 13, 14, 9, 11, 10 (NATH-12 backlog) · Claude

North star: Nathan is the brain-dead-simple way to protect a Cloudflare Worker and ask user.can("invoices:write") inside it. Sign-in methods (social, SAML) and SCIM only feed identities and groups into that model.

Approach: six stacked draft PRs, one per issue, landing in dependency order. Fix the broken login paths first and prove them in the Workers runtime (workerd). Then build the RBAC primitives that make protecting a Worker worth it, and add federation on top. The same runtime test harness verifies every phase.

Decisions confirmed today

SAML

Inbound first (Okta, Entra ID, Google Workspace sign users into Nathan). Nathan as a SAML IdP is backlogged as NATH-12.

SCIM

Finish inbound: link directory users to logins, revoke on deprovision, and map groups explicitly. No outbound provisioning.

Provider setup

One provider registry drives Identity Studio, the hosted installer and the CLI.

RBAC

Comes right after NATH-8. Apps declare permissions, roles bundle them, and roles are granted to users or groups. The gateway plus a one-line SDK is the default Worker path.

These change two NATH-1 launch decisions, which had deferred SAML and directory sync. The new issues record the change.

  3. 3 · Remote OAuth MCP servers with per-scope consent

    TodoNATH-14

    Any Worker can become an OAuth-protected remote MCP server with Nathan as its authorization server. This follows ForgeGraph's FORGE-396 and FORGE-401 design. The MCP server's RBAC permissions are its scopes. The consent screen shows one checkbox per scope, preselected from the request, plus Full access; sensitive scopes must be ticked on their own. A connections page edits or disconnects grants. Effective scopes are always the consented scopes intersected with the user's current RBAC permissions.

    // a Worker MCP server protected by Nathan
const mcp = nathanMcp(env, { resource: "https://tools.example.com/mcp" });
export default { fetch: req => mcp.handle(req, async (user) => {
  if (!user.can("tickets:write")) return mcp.insufficientScope("tickets:write");
  …
})};

Scope

✓ In

  • The six phases above, each as a draft PR
  • Runtime tests in workerd
  • Docs: providers, SAML and SCIM guides

✕ Out

  • Nathan as a SAML IdP (NATH-12)
  • Outbound SCIM
  • Auto-creating OAuth apps through provider APIs
  • Marking any PR production-ready before staging verification and independent security review

Risks

High samlify or xmldom may not run in workerd. Phase 3 opens with that proof-of-concept. If it fails, isolate SAML in a Container or a separate Worker and revisit scope before building the UI.

High Account takeover through email-based linking across providers. Link only on a provider-verified email; never trust X or unverified Discord addresses; SAML and SCIM linking require a verified domain.

High Better Auth's resources list is static, so per-app MCP audiences may not fit inside it. NATH-14 opens with a spike. The fallback is a Nathan-owned grant and resource layer like ForgeGraph's, which keeps Better Auth for sign-in only.

Medium The Apple .p8 key is long-lived and powerful. Encrypt it under NATHAN_CONFIG_KEY with provider-bound AAD. Never return it from any API. Mint only short-lived client secrets.

Medium Unit tests can't stand in for real provider and IdP behavior. Every PR stays a draft until staging sign-in with real test accounts, per AGENTS.md.

Verification

Each PR must pass npm test, typecheck, the three Worker dry-run builds, verify:release and the new workerd suite. Staging checks with real provider accounts, an Entra or Okta SAML tenant and a SCIM directory stay listed as open gates on each issue.
