Nathan: dogfood gmacko apps, Kumo Studio behind Access, parent/child fleet Proposal

2026-11-22 · gmackie/nathan (+ create-gmacko-app) · base: NATH-16 stack tip, not main · Kanbanger project Nathan (GMA)

Recommendation: Run three tracks on top of the NATH-7…19 stack. A makes Nathan the upstream OIDC provider in the shared packages/auth template. Each app keeps Better Auth and its own sessions. B rebuilds Identity Studio as a Kumo React SPA on a dedicated admin hostname. Cloudflare Access is the admin session there; children use Nathan admin. C adds a parent fleet registry. Children enroll with the parent and choose to opt in, and they can federate identity from it. A and B start in parallel. C needs B's JSON management API.

What the repo says today

Base is not main

main trails feat/NATH-16-followups by 92 commits. That stack covers NATH-7 to NATH-19, including RBAC, SAML, SCIM, admission, tokens and MCP. Studio now spans about ten *-ui.ts files of server-rendered HTML. A rewrite started from main would conflict with every one of them.

Template is already OIDC-ready

create-gmacko-app/packages/auth already registers GitHub and Google through genericOAuth, next to expo(), bearer(), device pairing and its own MCP OAuth server. Nine repos carry this package: create-gmacko-app, creator, creator-d1, fabforge, fastbooks, kanbanger, netcontrol, preflight-app and wafflehouse.

Long tail is bespoke

About 40 more package.json files depend on better-auth with their own setup. ForgeGraph's web app is one of them. For these apps the change is still small, but each needs its own PR, not a template sync.

Kumo

@cloudflare/kumo 2.19.0 (npm) is a React 18/19 library built on Base UI. Its peer dependencies are echarts, @phosphor-icons/react and zod 4. Nathan has no React or bundler today, so this adds a frontend build.

  4. C. Fleet: parent manages and federates children

    Todo
    1. 1Register: a parent admin creates an instance record and gets a single-use, expiring enrollment code bound to the child's issuer.
    2. 2Child consents: a child admin pastes the code into the child Studio and sees exactly what the parent gets: federation, read scopes, admin scopes. Each one is toggled separately.
    3. 3Federation: the child adds the parent as an enterprise OIDC upstream with an exact issuer, pinned through JWKS discovery. Subjects are issuer-qualified. Child admission policy still applies. Auto-admitting parent users is a per-child switch.
    4. 4Management credential: the child registers the parent as a client_credentials client using private_key_jwt. The parent's key stays on the parent. Scopes are fleet:read and fleet:admin.users, .apps, .roles. Tokens are audience-bound to the child's management API and last 900 s or less (NATH-15 token profile).
    5. 5Operate: the parent Studio's fleet pages show health, version and counts, and proxy admin actions to the child API. Every write is audited on both sides with the acting parent admin's identity. The child can revoke at any time, and revocation takes effect immediately.
    6. 6Child admins: a parent identity becomes a child admin only through an explicit grant on the child. Holding parent admin is never enough.

    What the parent can never reach: child signing keys, provider and client secrets, password hashes, session tokens, the MFA policy floor, and Cloudflare credentials for customer accounts. For own-domain children, the parent may also deploy a child through the existing installer, with the operator's own Cloudflare OAuth.

  5. D. Customer-account children

    Todo

    Same protocol with stricter defaults. Federation and admin delegation are both off. The child Studio shows a persistent banner while a parent link exists. Revocation and key-rotation drills are part of staging acceptance. This phase gets its own independent security review before any customer enrollment.

Mitigations
  • R1 Access protects a hostname, not the Worker. Verify the Access JWT inside the Worker on every /studio/api request, on any host. Tests cover workers.dev, preview and login-host requests.
  • R2 Federation means a compromised parent can sign in to every federated child. Mitigations: per-child opt-in, admin power only through child-side grants, scoped short-lived management tokens, two-sided audit, immediate revocation, and the parent admin host behind Access with hardware-key MFA.
  • R3 Link by email only on email_verified from a trusted provider, and only once. After that, key on sub. Check Nathan's social providers (X has a placeholder email) so they never assert verified email.
  • R4 Extract the API first (B1) with no behaviour change. Keep the HTML Studio until the parity checklist is complete.
  • R5 Register the exact Expo scheme redirects. Verify on the simulator before the fleet sync.
  • R6 The Access IdP must not be Nathan itself; use GitHub or one-time PIN. Cloudflare-owner-bound recovery stays as break-glass.

Decisions to confirm

1. Changes to the security invariants. Access mode replaces Nathan's verified admin session and passkey step-up for the dashboard. The admin identity then comes from Access's IdP, which still needs a verified email and an explicit allowlist. Nathan can't see whether MFA was used. Unless Access verification shows a reliable amr claim, MFA rests on the Access policy, checked by the installer when it creates the app. Proposal: amend AGENTS.md and docs/security.md for Access mode, and treat it as an item for the independent security review.
2. Which instance is the parent, and does it serve app users? Proposal: one parent for the gmacko apex that is also the dogfood issuer for every gmacko app. OIDC doesn't need the app and the issuer on the same apex. Per-apex children come later, only where a separate realm is needed.
3. Pilot app for track A. Proposal: kanbanger. It's on the template, used every day, and the cost of a bad rollout is low.
4. Base strategy. Proposal: finish staging verification and merge NATH-7…19 first (P0), rather than stacking more drafts on drafts.
