Build a small, isolated executable proof against the pinned Better Auth 1.7.14 packages before implementing shared access in the production Workers. Prove that authorization, code exchange, refresh and MFA all consult the intended policy. This document specifies that future task; no fixture, runtime implementation or test has been executed during planning.

Nathan runs in the operator’s Cloudflare account. Launch requires a CLI installer, browser-guided external OIDC setup, protected Workers, Grafana and an independent reference web app. Required authentication is Google/GitHub, passkeys, TOTP, email/password and enterprise OIDC, first verified with Microsoft Entra ID. Signup is installation-configurable and invitation-only by default. Nathan manages users/groups; each app chooses approved-users/groups or any active signed-in user and independently chooses end-user MFA. Administrators always need MFA. SAML and directory sync are deferred.

The confirmed population is 51,000 users; 500 apps, 1,000 simultaneous sign-in flows and 5,000 protected requests/second are proposed targets. Worker revocation must take effect within 60 seconds of committed user blocking, app disable or final-grant removal. New OIDC grants check current policy; existing external sessions have a separate measured boundary. Public beta follows security/end-to-end gates; production support follows a monitored pilot.

Decision: continue with the pinned provider while testing its real extension points. Do not design around an invented “before token” provider callback, rewrite standard grant handlers, or change provider-owned MFA claims. A failed proof becomes an explicit design decision about an upstream change, reviewed patch or alternative provider.

Phase 2: prove or reject the candidate design

2 · POLICY AND EVIDENCE

Check every grant path, including continuations and retries

Evaluate a companion plugin combining endpoint hooks, a narrowly filtered final-code storage guard and a verified-context token contributor. A token before-hook may deny based on an authoritative stored grant, but must delegate all positive protocol decisions to the provider. Do not duplicate internal token codecs, consume a grant twice or accept browser-supplied user/app identifiers.

If the token contributor is used as a deny guard, constrain launch to user code/refresh flows with effective openid, an explicit client-to-app mapping and zero refresh reuse grace. Test attempts to omit/drop openid, add a resource, use another grant or alter metadata. Fail startup or registration for unsupported configurations. Do not mark this design viable until the matrix passes with the exact package bytes.

Risks, stop conditions and open decisions

Stop and report if a required path bypasses supported hooks; a contributor can run after a usable token is exposed; safe invitation redemption needs an unsupported transaction; verified MFA cannot bind to the final session; or the selected design needs a provider patch. Include the failing request class and redacted trace. Do not replace the standard protocol with a raw minting primitive. The provider’s issueTokens API explicitly makes authorization the caller’s responsibility.

Still pending: the proven production hook composition and D1 transaction boundary, exact Worker caller/session transport, pinned live Grafana/reference-app fixtures and external-session bound. Token/session/MFA defaults and workload budgets are engineering proposals in the contract. Package distribution, email setup, pilot duration/thresholds and named support/security owners require release decisions. These open items do not prevent the isolated proof.

Maintenance: rerun this matrix after identity-package updates, hook reordering, scope/grant changes, refresh reuse changes, new account-creation paths or MFA recovery changes. Keep all fixture controls outside production import graphs. A green bundle or static SQL test is insufficient evidence of protocol enforcement.
