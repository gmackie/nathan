The first release must support both a protected Cloudflare Worker and an external OIDC application. Nathan runs in the operator’s Cloudflare account. Installation starts in a CLI wizard; external applications are connected through Identity Studio in the browser.

Confirmed release path: public beta after the security and end-to-end acceptance gates pass, followed by production support after a monitored pilot. Acceptance must cover larger installations. The user confirmed 51,000 users per installation. Proposed acceptance targets are 500 connected apps, 1,000 simultaneous sign-in flows and 5,000 aggregate protected requests/second, with separate 2× burst tests. These engineering targets have not been benchmarked; see the proposed capacity profile. See the beta, pilot and capacity gates.

Cost and ownership research: the Nathan vs Clerk report compares sourced prices and explicit usage scenarios from 50,000 through 5 million users, including a simple Workers/D1 CRUD app, total app + auth costs and authentication’s share of the bill. It includes a calculator, sensitivity analysis and downloadable figures. Projections to 1M+ do not add a load-test requirement; the confirmed launch test population remains 51,000.

Agreed access rule: each application independently supports approved users/groups or an explicit “any signed-in user” mode. New apps grant no access until a policy is configured and enabled. Being signed in, sharing a domain, or having consented to OAuth does not select a policy automatically.

Confirmed scope

Initial installation · CLI

Select account and identity hostname → preview exact resources → deploy privately with secrets → establish the verified administrator and MFA → verify the installation.

The hosted Cloudflare deployment wizard is not required for this first launch.

External applications · browser

Register the application and exact callbacks → choose its access policy → save credentials securely → apply the supplied OIDC settings → complete and verify a real login.

Nathan itself is not being ported to non-Cloudflare hosting.

Worker protection and external OIDC are both required. This launch plan evaluates the existing implementation branch as reusable starting material; the canonical main checkout contains the original README. Existing code is not treated as verified release evidence.

Account admission

Confirmed: each installation supports invitation-only and self-service signup. Invitation-only is the default; an administrator must explicitly enable self-service signup. This setting governs creation of Nathan accounts across email/password, social sign-in and enterprise OIDC, including first-login account provisioning.

Account admission and application access are separate decisions. An admitted, active user can use an enabled any-signed-in-user app after satisfying any configured MFA requirement; an approved-users/groups app also requires its own matching grant. Changing signup mode must not change any application's policy or grant administrator privileges. Existing active users can continue signing in when new account creation becomes invitation-only.

Worker revocation measurement: start the clock at the successful authoritative commit of a user block, app disable or final matching-grant removal. Any protected request whose authorization occurs 60 seconds later must deny. Account for D1 read consistency, replicas, isolates/regions, cache expiry and races with old policy responses. Traffic must not renew an old allow, and failed revalidation must not extend it. Requests already authorized before the bound are not recalled; streaming and long-lived connections need an explicit supported behavior or must be excluded from the launch guarantee.

Both policy modes are confirmed for launch, chosen separately for each application. Approved user/group mode requires an explicit matching grant; an empty approved list denies everyone. Any-signed-in mode allows an active authenticated identity without an application membership grant, only after explicit selection. Unauthenticated or blocked users, disabled apps and missing policies still deny. Administrator privileges do not imply access to all applications. Directory staging in SCIM is not an authoritative grant source.

The access mode is separate from OIDC’s public/confidential client setting, which describes whether a client can protect a secret. Choosing any-signed-in access does not enable self-service signup or change client authentication. Policy changes affect only the chosen application and obey the documented session/revocation bounds.

Users and groups · Nathan is authoritative

Confirmed: administrators manage Nathan users, groups and membership in Identity Studio. Approved-users/groups application policies use this Nathan-managed membership. Directory synchronization and Entra group mapping are deferred; enterprise sign-in does not import, replace or create access grants from upstream group claims.

Proposed first model: flat groups with explicit user memberships and application grants to stable Nathan user/group IDs. Avoid nested groups and dynamic membership rules in the first implementation. Group names and email addresses are display values; renaming or account linking must preserve the intended identity without transferring access.

Administration journeyAcceptance requirement
Manage groups and membershipCreate, rename and remove a group; add and remove members; inspect its application grants. All writes require authorized administration and audit. Ordinary users cannot join a granted group or change their own access through raw APIs or organization-plugin roles.
Assign app accessChoose explicit users and groups in the app's approved-users/groups policy. Proposed semantics: any matching explicit grant suffices; removing one group membership does not cancel an independent user or group grant.
Remove a membership or groupReevaluate all affected apps under the documented revocation bounds. A deleted group cannot keep granting access; a new group with the same name does not inherit its grants. Removal alone does not block the user account or revoke access to any-signed-in-user apps.
Block a userDeny that user in both app modes under the user-disable/session contract. Account admission, app membership and user blocking are separate operations.

Storage schema, supported dependency hooks, exact administrator permissions and audit transaction behavior still need a concrete design. Better Auth organization membership, a global role, an Entra claim and a staged SCIM record cannot implicitly become a Nathan application grant.

MFA · mandatory for administrators, chosen per app

Confirmed: administrators must complete MFA before privileged administration. Each app separately chooses whether its end users must complete MFA. This requirement applies to either application access mode and every enabled sign-in method; app membership and successful Google/GitHub or Entra authentication do not automatically satisfy it.

BoundaryRequired behavior
Administrator accessAll supported privileged Studio, API and management paths require verified session-bound MFA. Enrollment alone and legacy configuration fallbacks cannot count as completed MFA. Define and test recent reauthentication for sensitive operations.
App with MFA requiredAn otherwise entitled user needs sufficient verified evidence bound to the active principal/session before protected access or a new app grant. Offer a supported enrollment/challenge journey when evidence is absent; cancelled or failed challenges do not allow access.
App without MFA requiredDo not add an app-specific MFA challenge. Account status, application policy, protocol checks and mandatory administrator MFA still apply.
Policy change, refresh and recoveryEnabling MFA reevaluates weaker existing sessions under the measured freshness contract. Token refresh cannot invent or renew MFA evidence. Authenticator removal, recovery and remembered-device behavior must follow an explicit policy without silently lowering assurance.

Proposed launch evidence model: rely on Nathan-verified authentication ceremonies. Accept primary authentication plus a verified TOTP challenge, or a passkey ceremony only if the supported factor model and verified user-verification result justify satisfying MFA. Mere passkey possession or enrollment is insufficient. Defer trusting upstream MFA claims until provider-specific verification and mapping are designed and tested.

The contract must specify accepted factor combinations, evidence/session binding, challenge age, revocation and recovery. Preserve the actual meanings of acr, amr and auth_time; use explicit evidence for MFA completion time rather than rewriting a primary authentication timestamp. Unsupported or missing evidence fails closed where MFA is required. This feature does not imply NIST AAL2/AAL3 or another assurance certification.

Recommended delivery order

These are proposed work packages, not completed implementation or verified deployment. No dates are estimated before the real integration baseline is measured.

0 · CONTRACT AND BASELINEDefine the application/client/policy contract

Specify both agreed access modes, Nathan-managed users/groups, mandatory admin and per-app MFA, stable identity mapping, every enforcement point, and revocation guarantees. Use the source-backed draft contract and execute the isolated Plan 002 proof before specifying production changes. Create real staging fixtures for a Worker, externally hosted Grafana and a reference OIDC web app; include the confirmed 60-second Worker revocation bound.

Exit: agreed semantics and test cases, supported integration points identified. Plan 001 design checklist → Plan 002 executable proof → gated Plan 003 production integration.

1 · ENFORCEMENTImplement shared default-deny application access

Bind clients and gateways to applications, implement authoritative policy and MFA evaluation plus privileged local group/member/grant management, protect registration/status changes, and cover cross-app access and concurrent policy changes.

Exit: the same identity and sufficient authentication evidence produce consistent decisions for a given app through either integration; no bypass through raw protocol endpoints.

2 · INSTALLATION AND ONBOARDINGMake the CLI and Studio journeys complete

Handle CLI interruption, resource ownership, retries and accurate completion states. Replace raw client JSON as the main browser experience with guided OIDC setup, clear credential handling and an actual connection test.

Exit: an independent operator installs Nathan, protects a Worker and connects an external app using the shipped instructions.

3 · SECURITY AND OPERATIONSProve lifecycle behavior and recovery

Test bootstrap ownership, current-session admin MFA, user blocking, refresh replay, logout delivery, signing-key rotation, failed email, D1 outages, backup restore and upgrades with existing users/clients.

Exit: measured, documented failure and recovery behavior; unresolved security findings have explicit release impact.

4 · PUBLIC BETAPublish only after security, journeys and capacity acceptance

Verify the versioned CLI artifact, provenance and dependency inventory. Pass the Worker/Grafana/reference-app journeys and measured revocation/failure tests at the agreed larger-installation profile. Publish the supported configuration and known operational limits.

Exit: reproducible install and exact-revision evidence; larger-installation numbers must be agreed and measured before claiming capacity.

5 · MONITORED PILOT → PRODUCTIONValidate real operation before production support

Monitor representative installations, repair setup and lifecycle failures, and exercise upgrade, restore, incident response and key rotation. Complete independent security review, remediate release blockers, and assign security-update and support ownership.

Exit: a recorded pilot review against agreed duration, workload and reliability thresholds; a documented production-support decision. A beta label or elapsed time alone does not pass the gate.

Deferred scope and remaining product decisions

Confirmed deferral: enterprise SAML; launch federation uses OIDC. Google/GitHub, passkeys/TOTP, email/password and enterprise OIDC are all required. Microsoft Entra ID is the first live enterprise acceptance target. Signup is configurable per installation and invitation-only by default. Nathan-managed users/groups are authoritative; directory synchronization and Entra group mapping are deferred. MFA is mandatory for administrators and configurable independently per app. The downstream live acceptance targets are Grafana and a reference web app alongside the protected Worker. Worker revocation has a 60-second maximum; external-session behavior is measured separately.

Recommendations, not yet accepted requirements: start downstream application support with confidential server web applications using code + S256 PKCE; defer mobile/native, device and machine flows, arbitrary plugin installation, MCP writes and high-assurance claims unless explicitly selected.

Choose email setup, exact token/session lifetimes and external-session limits, the proposed workload and latency/error budgets, pilot exit thresholds and security-update ownership. The public-beta → monitored-pilot → production-support path and larger-installation acceptance scope are confirmed. MFA factor composition, evidence binding, challenge age and new-app MFA defaults, local group/grant storage, exact administrator permissions, invitation ownership, expiry and redemption mechanisms still need a concrete design. The monitored pilot is required before production support; it must satisfy agreed acceptance thresholds.

Considered and rejected as findings: parent-domain cookie sharing and automatic wildcard app approval are already deliberately excluded. SCIM staging is a documented limitation; it is not described here as implemented login deprovisioning. No new runtime vulnerability is claimed without a reproducing test. docs/providers.md has older enterprise-UI wording; use the current source and docs/setup-lifecycle.md when designing the OIDC admin journey, and reconcile the contradictory docs before launch.
