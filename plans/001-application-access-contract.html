Executor objective: produce a verified application-access contract and a follow-on implementation plan. This is a design/spike milestone. Do not retrofit authorization into runtime code from this document alone.

Nathan is a customer-owned Cloudflare Workers/D1 identity provider built on Better Auth 1.7.14. The first public release requires both Worker protection and external OIDC. The operator installs Nathan with a CLI wizard and onboards external applications through the browser. The user has agreed that every application requires explicit policy and defaults to deny until configured. Both approved-users/groups and explicit “any signed-in user” access are required at launch, chosen separately for each application.

Confirmed sign-in scope: Google/GitHub, passkeys and TOTP, email/password, and enterprise OIDC federation are all required. SAML is deferred. Account creation, provider linking and recovery must never bypass the same application policy or grant administrator access implicitly. Upstream enterprise SSO is separate from downstream application OIDC registration and from directory provisioning.

Confirmed enterprise acceptance provider: Microsoft Entra ID. Use its real tenant, issuer, app registration and signed assertions when validating compatibility. Do not treat generic OIDC settings or successful discovery as evidence that Entra sign-in and downstream access work. Credential collection and live deployment are separate implementation/acceptance work, not part of this planning milestone.

Confirmed account admission: support invitation-only and self-service signup per installation; invitation-only is the default. An administrator explicitly enables self-service. Apply admission to first-time password, social and enterprise OIDC account creation, including direct API and callback paths. Admission does not create app grants or administrator privileges. Existing active users can sign in when registration becomes invitation-only; blocking a user remains a separate operation.

Confirmed membership authority: Nathan users, groups and memberships are managed by administrators in Identity Studio. Approved-users/groups policies use Nathan-managed membership; directory synchronization and Entra group mapping are deferred. Proposed launch model: flat groups with direct members and explicit user/group grants, using stable Nathan IDs. This is a proposed schema/semantics choice, not a claim that the current organization plugin implements it.

Confirmed MFA scope: mandatory for administrators and separately configurable per app for end users. The MFA requirement is independent of approved-users/groups versus any-signed-in-user access and applies across all enabled login methods. Define actual session-bound authentication evidence; enrolled credentials, upstream sign-in success and a global admin role do not prove the current session completed MFA.

Confirmed live targets and revocation: a protected Cloudflare Worker, externally hosted Grafana and a small reference web app. Nathan-controlled Worker access must deny newly authorized requests within 60 seconds of committed user blocking, app disable or removal of the final matching grant. New OIDC authorization, exchange and refresh check current policy. Grafana/reference-app sessions have separately measured limits; do not apply the Worker bound to them by assumption.

Confirmed release and scale: public beta after security and end-to-end acceptance, then production support after a monitored pilot. Test larger installations. The user confirmed 51,000 users per installation and requested proposed targets for the remaining dimensions: 500 connected apps, 1,000 simultaneous sign-in flows and 5,000 aggregate protected requests/second, with separate 2× bursts. These values remain proposed and unmeasured; see the self-contained capacity profile. Do not assume the smaller offered profiles or claim capacity from unit tests. The shared policy, membership lookup and cache design must remain correct under the agreed data size and concurrent revocation load.

Why this must come first: the existing gateway validates a login session, the private binding evaluates global roles, and OAuth registration does not define their common application policy. Refactoring just the UI or one enforcement path would leave incompatible access behavior.

Phase 2: write the shared policy contract

The draft JSON contract now records 18 confirmed/proposed decisions, ten enforcement surfaces and 40 mapped acceptance cases. It remains an execution-gated draft. Maintain baseline, decisions, enforcementPoints, revocationContract, cases and openQuestions. Each unconfirmed decision remains explicitly marked proposed or pending.

  1. Define application as the protected logical app, client as an OIDC registration mapped to it, and policy as the explicit conditions for app access. Decide whether one app may have multiple clients; require unique authoritative mappings, never infer authorization from a hostname suffix.
  2. Define stable verified principal identity. Subject IDs and authoritative membership are the grant basis; email changes and provider linking cannot transfer access accidentally. An email/domain rule, if chosen, requires verified claims and a separately stated threat model.
  3. Implement the two confirmed policy modes in the contract: approved users/groups and explicit any-authenticated access, selected independently per application. Missing, empty, invalid or disabled policy denies. An empty approved list denies; it never aliases any-authenticated. In any-authenticated mode an active authenticated identity does not need a membership grant, but blocked users and disabled apps still deny. Global admin role, OAuth consent and SCIM staging never create implicit membership. Keep the access mode separate from OIDC publicClient/client authentication and from account signup policy. Neither one may be inferred from another.
  4. Define activation and disable behavior across normal Studio registration, realm/batch registration, CLI/gateway provisioning and every direct protocol route. Unlinked or partially created clients cannot grant access.
  5. Specify current-policy checks at authorization, exchange and refresh; include policy changes between these steps. For gateways and binding authorization, use authoritative decisions with a measured bounded cache at most. Missing state, backend errors and stale untrusted decisions fail closed.
  6. Specify token/session expiry and invalidation per integration. Distinguish app disable, user disable, grant removal, client disable, refresh revocation and global logout. Record a maximum freshness interval and its evidence for each supported integration. Never promise control over an arbitrary external app’s independent session.
  7. Separate authentication from app authorization and app-local permissions. Document what a valid OIDC login proves and what the relying app must enforce itself.
  8. Record the confirmed installation-wide admission modes separately from application policy: invitation-only by default, self-service only after explicit administrator opt-in. Specify invitation ownership proof, expiry, revocation, single-use/concurrent redemption and safe bootstrap. Unknown or unavailable admission state fails closed for new accounts. A signup-mode change does not alter existing grants or turn active users into blocked users. Any explicit invitation-associated app grant must be a distinct, privileged authorization action.
  9. Specify Nathan-managed users/groups as the authoritative grant source. Propose flat groups with direct user membership and OR semantics across explicit user/group grants; label these modeling choices proposed until finalized in the contract. Define stable IDs, rename/delete/recreate behavior, member removal, privilege checks, audit and concurrent writes. Directory sync and upstream group mapping are deferred. Group removal never overrides another valid grant or independently blocks a user; user blocking remains authoritative in both app modes.
  10. Record mandatory administrator MFA and independent per-app MFA as confirmed. Specify a server-controlled requirement and a verified evidence record bound to the correct principal/session, with accepted factor composition and completion time. Propose Nathan-local evidence for launch: primary authentication plus verified TOTP, or a qualifying passkey ceremony with verified user verification after investigating the supported factor model. Upstream MFA-claim mapping remains proposed for deferral until explicitly verified. Enrollment alone cannot satisfy the requirement. Preserve protocol claim meanings and do not claim AAL2/AAL3. Define challenge freshness, policy changes, refresh, recovery, remembered devices and authenticator revocation without inventing new evidence.
  11. Record the confirmed 60-second maximum for Nathan-controlled Worker revocation. Measure from successful authoritative mutation commit to denial for requests authorized at or beyond that deadline; include user blocking, disabled apps and removal of the final matching grant. Specify trustworthy read freshness, fixed cache deadlines, continued traffic, isolate/region changes, stale responses, failure handling and long-lived connections. New OIDC grants require current-policy checks at authorization, exchange and refresh; existing external app sessions remain a separate measured contract.
  12. Size policy, group and grant queries against the agreed larger-installation profile. Record users, apps, groups/memberships, active sessions, login/refresh/Worker request rates and policy-write rate separately. Require bounded indexed lookups and complete authorized directory search/pagination; never serialize an entire membership list into a client cookie or assume one isolate holds all revocation state. Latency/error/workload targets in plans/capacity-profile.html remain proposed until measured; establish cost limits from the measured baseline.
